# Standard — Specs & ticket tracker (local-first)

The `pm-planner` and `tracker-sync` agents record work as a **spec source**, not a specific
product. The default and priority source is **local Markdown specs in the repo**; JIRA (via
the Atlassian MCP) is an optional target when the team wants tickets synced there. The same
workflows must work on either, so always go through this abstraction.

## Ask first — always (mandatory gate)

**Never assume where specs go.** Before creating anything, **ask the user** whether to write:

- **Local Markdown specs** (default, recommended) — files under `specs/`, versioned with the
  code, no external tool needed. **Prefer this even when a JIRA MCP is configured.**
- **JIRA** — create/transition issues via the Atlassian MCP.
- **Both** — local specs as the source of truth, mirrored into JIRA.

Ask this **every time**, even if the Atlassian MCP is available — having the MCP configured
is not consent to use it. Default to local specs if the user has no preference.

## Reuse existing specs (check before generating)

A project may **already contain specs** — hand-written, or generated by another tool and
copied into the repo. **Look first:** scan `specs/` (and common spots like `docs/specs/`,
`docs/`) for existing epic/US Markdown. If found:

- **Do not regenerate or overwrite.** Read them, treat them as the source of truth, and
  continue from there (add missing stories, fill gaps, update statuses).
- If their layout differs from the convention below, **propose** normalizing into it — don't
  restructure silently; ask the user.

## Local spec layout

```
specs/
  epic-01-<slug>/
    epic.md              # the epic: problem, scope, success criteria
    us-001-<slug>.md     # one user story per file
    us-002-<slug>.md
  epic-02-<slug>/
    ...
```

- Epics: `epic-<NN>-<slug>/`; user stories: `us-<NNN>-<slug>.md` inside their epic folder.
- Zero-padded, incrementing ids (`epic-01`, `us-001`); never reuse an id.
- Each **US file** carries: title, user-story statement, acceptance criteria
  (Given/When/Then), estimate (S/M/L), dependencies, layers touched, and a `status`.
- Keep it minimal — the file *is* the ticket; no ceremony. Start from the templates in
  `specs/_template/` (`epic.md`, `us-000-template.md`).

## Canonical model

Map either source onto this neutral model; never leak JIRA (or file) field names into the
workflow logic:

| Canonical     | Local spec                          | JIRA                        |
|---------------|-------------------------------------|-----------------------------|
| `id`/`key`    | `us-001` / folder+file path         | issue key (`PROJ-123`)      |
| `title`       | file title (`# …`)                  | summary                     |
| `description` | file body                           | description                 |
| `status`      | `status:` field in the file         | status (workflow)           |
| `type`        | epic folder vs `us-` file           | issue type (Story/Epic)     |
| `parent`      | the `epic-NN` folder                | epic / parent link          |
| `url`         | repo-relative path                  | browse URL                  |

Statuses map to the generic stages **To Do → In Progress → In Review → Done**. For JIRA, read
the real workflow and use the project's actual names; never invent one. For local specs, use
those four in the `status:` field.

## Rules

- **Ask before choosing the source** (see the gate above) — every run.
- **Reuse before create.** Check for existing specs/tickets first; update rather than
  duplicate. Match on id/title.
- **Read before write.** Fetch current state before transitioning or editing.
- **Least surprise.** Bulk changes, deletions or re-assignments are **proposed**, not applied
  silently — confirm unless told to proceed.
- **Traceability.** Reference the spec id / issue key in branch/commit/PR; surface the `url`
  (path or link) in reports.
- **No secrets.** OAuth/tokens live in the MCP config, never in code or in a spec/ticket body.
